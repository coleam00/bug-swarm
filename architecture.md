# Architecture

## Stack
- Bun (runtime, package manager, test runner), TypeScript strict, Vite for the browser build, Canvas 2D for the game, Hono on Bun for a small API, SQLite through `bun:sqlite` for runs and scores.
- Why: the bootcamp's supported stack, with the same commands on Windows, macOS and Linux. A game loop needs no UI framework; the server exists for the shared leaderboard and the bet.
- The scaffolded React screen stays only as a thin shell for name entry, upgrade choices and the game-over screen around the canvas. No React in the game loop.

## How it runs
- Install: `bun install`
- Develop: `bun run dev` (Vite dev server for the game, with the API server beside it)
- Start (production mode): `bun run build` then `bun run start`: one Bun process serves the API and built UI from `dist/` on `0.0.0.0` and `PORT` (default 3000). `bun run dev` keeps the API on `127.0.0.1`. `/board` (also `/board/`) is the stream display in both modes.
- Container: `Dockerfile` builds the game and runs `bun run start`; `DATA_DIR` must be a persistent volume.
- Health: `GET /health` answers `200 ok` once the app is ready.
- Sharing: `/favicon.svg` is a procedural robot; `/favicon.ico` embeds its 32 px PNG, `/apple-touch-icon.png` is 180 px, and `/og-image.png` is a 1200 x 630 arena composition. `src/server/share-assets.ts` generates these once at startup with the server-only `@resvg/resvg-js` rasterizer (no fonts or external resources), then serves cached bytes with `public, max-age=3600`. No generated art files are committed or loaded by gameplay. Vite forwards these exact routes to the API's `PORT`, including before the first build.
- Initial HTML includes the description, dark theme and Open Graph/Twitter cards. `PUBLIC_ORIGIN` takes precedence over `https://` plus Railway's `RAILWAY_PUBLIC_DOMAIN`, then the incoming request URL's origin in production. Configured origins are validated before opening SQLite; forwarded host/proto headers are ignored. Set `PUBLIC_ORIGIN=https://your-domain.example` for custom domains, or `http://your-lan-host:5173` for remote/LAN development. Only HTTP(S) origins are accepted, with an optional trailing slash. Local development needs no environment file: Vite uses its actual frontend URL/port. Built HTML keeps placeholders until the production server substitutes the origin, including `/index.html`, both board routes and SPA fallback; all cards describe the root game URL.
- Test everything: `bun run check` (`tsc --noEmit`, then `bun test`). CI runs exactly this.
- Pacing: `bun run pacing` runs 20 deterministic, upgrade-enabled idle/evasive cases in portrait and landscape, prints times/builds/medians/maxima and fails if idle exceeds 60 seconds, evasive medians leave 60–180 seconds, any run exceeds 240 seconds, or scoring fails server validation. `bun run pacing --broad` crosses seeds 0–99 with all five full priorities, both shapes and both modes (2,000 runs); both modes choose by priority. It additionally requires an overall evasive median of 75–110 seconds and every priority’s evasive median ≥55 seconds, retaining the idle/death/score ceilings. It prints every mode/shape/priority grouping and evasive deaths under 60 seconds. CI keeps the default targets and checks a ten-seed broad slice. See [docs/pacing-validation.md](docs/pacing-validation.md) for definitions and before/after evidence.
- The bet's command: `bun run stats`. Moderation: `bun run hide "<name>"`. Capacity: `bun run load -- --url <base url>`. Pre-stream cleanup: `bun run reset -- --yes`.

### Container

Build and run with a persistent data directory:

```sh
docker build -t bug-swarm .
docker volume create bug-swarm-data
docker run --rm --name bug-swarm-smoke -e PORT=8080 -e DATA_DIR=/data -p 8080:8080 -v bug-swarm-data:/data bug-swarm
```

Open `http://localhost:8080/`; `http://localhost:8080/health` answers `200 ok`.
The image builds the web bundle and runs `bun run start` in production mode.
Without `DATA_DIR`, the default relative `data/` directory resolves to `/app/data` in the image.
Persistent deployments should mount their chosen `DATA_DIR`; the example stores `/data/app.db` in the named volume and reuses it across restarts.

## Shape
- Browser game -> HTTP API -> one SQLite file.
- `src/web/App.tsx`: name and permanent team entry, the canvas/HUD, the game-over screen with the team race directly under the score. Play again precedes the upgrade summary and top 10.
- `src/web/game/`: the game in plain TypeScript.
  - The simulation (robot, bugs, shots, hits) is pure: it advances by a time step from input and seeded state, with no canvas, DOM or clock access, so `bun test` covers it. Spawn intervals interpolate through (seconds, interval): (0, 0.2), (20, 4), (30, 4), (60, 0.3), (120, 0.2), (180, 0.18). After 180 seconds the interval is `1/6 + (0.18 - 1/6) * exp(-(time - 180)/60)`, approaching six spawns/second from below. The brief opening base-bug burst gives way to relief around the first upgrade and fast-bug unlock, then the original late ramp resumes at 60 seconds. Both kinds' movement speeds multiply by `1 + max(0, time - 45)/45 + (max(0, time - 90)/45)^2`, so pursuit keeps accelerating for existing and new bugs. The first scheduled spawn at or after 30 seconds is fast, followed by every fourth eligible spawn. Bug definitions (speed, radius, color and unlock time) and pacing constants live in `src/web/game/config.ts`. Both bug kinds die in one shot. Four upgrade rules extend this same simulation; see the upgrade lifecycle below.
  - `draw.ts` owns the procedural renderer; `assets.ts` caches the full rectangular world's grid and vignette, glows and one eleven-cell score atlas (`+`, digits 0 through 9) on detached canvases. Numeric totals compose cached cells without per-frame text rasterization or a cache per total; labels retain at least an 18 CSS px font. All backing stores release on replacement/disposal. The foreground robot pass follows bugs, shots, particles, vignette, bomb, drones and labels: a cached 88-unit halo, dark-backed mint identity ring (radius 22) and rounded chassis remain readable even without a shield. Cache keys include canvas size, DPR and run geometry. `styles.ts` holds the beetle colours, dimensions and gait for both base and fast kinds; the fast beetle is smaller, brighter and quicker. Collision radii still come from `config.ts`.
  - `fx/` owns fixed-capacity particles (1024), trail samples (128), floating labels (12), hit flash, shield-block flash and shake. Squashes merge into the nearest label within 40 logical world units of its original anchor and 250 ms of its first emission (inclusive; slot order breaks ties). Merges add ten points without moving the anchor or renewing the 650 ms rising/fading lifetime. A full label pool still accepts merges and drops only unmatched cosmetic labels; scoring and particles remain independent. Fixed numeric totals/anchors reuse storage. Other full pools drop new emissions and reuse expired slots. The read-only scored-kill checkpoints and fixed-step comparisons in `fx/feedback.ts` distinguish scored kills from contact damage without changing simulation rules or its random seed. Visual time freezes during upgrade choices, continues after death and resets with focus/run lifecycle.
  - The loop runs on `requestAnimationFrame` with a fixed time step and draws the state to the canvas, scaled to the screen in portrait or landscape.
  - Input: touch uses a floating joystick whose first contact fixes its origin in canvas-local CSS pixels. A radial 6 px dead zone stops movement; speed increases continuously as `(distance - 6) / 54`, reaching full speed at 60 px. The knob is radially clamped to 60 px; the origin never slides, even at an edge or during captured movement outside the canvas. The first accepted pointer owns control until release; other fingers cannot change or take over that contact. Nonzero WASD/arrow direction takes priority, then an active touch (including its stationary dead zone), then mouse/pen targeting. Touch clears the previous mouse target and suppresses mouse movement until release; a fresh mouse event restores targeting. Directional `Input.speed` defaults to 1 and clamps to 0..1 without changing vector normalization; mouse targets retain their no-overshoot stopping. F shows the rolling FPS, current bug/live-effect counts and update/draw-time readout, refreshed once a second while visible. Live effects count particles, trail samples and floating labels, plus one each for an active bomb ring, hit flash, shield-block flash and shake; shots, drones, charged shield outlines and the joystick are excluded. Each run samples the browser viewport at start: its arena keeps 360,000 logical units squared and follows the viewport aspect ratio, clamped to 9:16 through 16:9. Rotation rescales the active arena and cancels touch until a fresh down; the next run adopts the new shape. Desktop steering survives resize.
  - The joystick's translucent 60 px ring and 12 px knob draw after restoring the world's transform and clip, in CSS coordinates under only the DPR transform. They do not shake or receive the vignette, and naturally clip at canvas edges. Two procedural circles add constant work independent of swarm size; no React frame updates or new caches are involved. Evidence: [docs/touch-validation.md](docs/touch-validation.md).
  - The API client starts a run and submits its score without blocking the loop; failures are logged and the game-over screen says the score wasn't saved. A refused start (HTTP 429) instead says “Too many runs right now. Your next run will save.” Restart remains available after the 800 ms input guard; that copy does not guarantee admission or saving on the next attempt.
- `src/web/game/session.ts`: asynchronous run lifecycle, immutable finish payloads, save/read status and polling. Gameplay starts immediately. Saving waits until monotonic time since the server's start acknowledgement covers the submitted gameplay seconds, a conservative lower bound on server elapsed time that accommodates registration latency without changing scores or adding server slack. After the 800 ms input guard, replay never waits for an earlier run's save. Best, leaderboard and team totals refresh independently on death and acknowledged save; leaderboard and teams poll every two seconds while subscribed on game over. Late responses and start-refusal reasons stay attached to their original local run, and only a newer applied response supersedes an older response. Refused starts never submit a finish. Restart and detachment stop polling. Requests time out after five seconds; no offline submission queue or rate-limit cooldown.
- `src/web/route.ts`: dynamically loads the stream board for `/board` and `/board/`, or the game elsewhere. The board never imports the game screen, engine, identity storage or game CSS.
- `src/web/page.css` prevents page overscroll on both views. Game CSS prevents UI selection/callouts while retaining name editing, canvas steering and scrolling result/upgrade overlays; buttons use `touch-action: manipulation`. The board retains ordinary vertical scrolling. Chrome emulation evidence and its WebKit limitation: [docs/share-validation.md](docs/share-validation.md).
- `src/web/board/`: read-only React stream page with the server's top 10 and Tabs vs Spaces totals. `model.ts` validates snapshots, preserves returned ordering, maps proportional race bars and owns three-second arrival/overtake highlights. `polling.ts` reads both endpoints immediately and every two seconds, independently; the shared API client's five-second deadline bounds overlapping reads. Only newer applied responses supersede older results. Failures retain that endpoint's last successful snapshot and retry after 2, 4, then 8 seconds (capped), with a small reconnecting note; recovery resets the cadence. Missing data shows waiting placeholders, distinct from successful empty/zero data. Cleanup invalidates pending responses and clears timers. The join link uses the page's own origin, in a prominent 36 px desktop join line. At 1280 px and wider, two ordered columns pair 40 px names with right-aligned 40 px scores on one line, above which team totals remain 64 px. Narrower screens use a scrolling column and allow long names to wrap beside their scores. Evidence and isolation limitations: [docs/board-validation.md](docs/board-validation.md).
- `src/server/app.ts`: `/health`, `POST /api/runs`, `POST /api/runs/:runId/finish`, `GET /api/leaderboard`, `GET /api/teams` (`{ tabs, spaces }` numeric totals), `GET /api/players/:playerId/best`, and the legacy `GET /api/events/count`.
- `src/server/db.ts`: the SQLite file, its tables and `EVENT_TYPES` (`run_started`, `run_ended`). It re-exports `TEAMS` from `src/shared/teams.ts`, the browser-safe registry of ids, names and colours (Tabs orange `#ff9f43`, Spaces teal `#2ed3c6`). Schema changes are additive.
- `src/server/rules.ts`: name rules and score plausibility (4.5 squashes per submitted gameplay second, at most 300 seconds, bounded by server elapsed time), both pure and tested.
- `src/server/blocked-words.ts`: the curated blocked vocabulary, reserved names and complete-name exceptions; `rules.ts` shares validation between browser entry, saved identities, board snapshots and server reads/writes.
- `src/server/main.ts`: production entry; reads `PORT` and `DATA_DIR` (default `data/`).
- `scripts/stats.ts`, `scripts/hide.ts`, `scripts/load.ts`, `scripts/reset.ts`: owner commands, capacity harness and confirmed gameplay reset.
- Tests are `*.test.ts` beside the code.

## Data
- **Player:** a random UUID the browser creates on first visit and keeps in local storage, with a validated name and a permanent team. No account. Names are fixed for an id; clearing storage creates a new player. Saved identities whose names fail current moderation require fresh name/team entry under a new UUID. Valid legacy identities keep their UUID/name and choose a team once on next entry; invalid stored teams also require selection. Choosing stores locally and starts immediately, even offline or when storage fails. Every start sends the saved team so an offline selection can reach the server later.
- **Start:** an immediate transaction validates the fixed name, assigns membership, snapshots the team on the run and records its event. New server players require a team (400 if absent); supplied invalid values including null return 400. Existing teamless players may omit it and still play, or assign it once. Assigned players may omit or repeat their team; name or team changes return 409. Failed starts roll back membership, run and event together.
- **Conflicting browser selections:** a team conflict returns 409 with `code: "team-conflict"` and the stored `team`. Session adopts that authoritative team, updates the browser identity without changing UUID/name, and retries the same local run's start once. This repairs stale entry tabs and already-conflicted saved identities, including on reload. Other start errors are not retried. Simulation starts immediately throughout; offline play and in-memory identity retention on storage failure still apply. The server never switches membership.
- **Run:** `run_started` (run id, player id, server time, nullable team snapshot) and `run_ended` (run id, score, squashes, seconds, upgrades, touch or not). A run with no `run_ended` was abandoned. Additive nullable `players.team` and `runs.team` columns restrict values to the shared registry. Existing rows stay null with no backfill: historical runs and runs started while teamless never count, even if finished after assignment. Finish cannot supply team attribution.
- **Hidden names:** a table the top 10 and the board filter on; `bun run hide` adds to it.
- **Top 10:** one best accepted score per player, excluding hidden names and names that fail current validation before taking ten. Ties go to the earliest finish achieving that best, then player id. Cached for one second and invalidated after a finish; game-over clients poll every two seconds. Personal bests and bet stats retain hidden, blocked and reserved players; board reads never delete or rewrite players, runs or events.
- **Team race:** sums every finished run with an eligible team snapshot, excluding hidden names and names that fail current validation (including duplicate names). SQL groups by player id/name and run-team snapshot; current name rules filter those groups at read time before adding them to team totals. It includes all scores, rather than personal bests or only ten players. Both keys appear as zero for an empty database. Totals have their own one-second cache, also expiring on backwards clock movement and invalidated on finish; all API reads use `Cache-Control: no-store`. Separate-process moderation appears through expiry and foreground polling within five seconds while reads succeed. On game over, team read failures clear the race and show unavailable text without affecting saves or restart. The stream board retains last-good totals during outages. Zero totals show a neutral equal split; positive totals use proportional bars with labels outside the segments. Chrome phone layout and moderation evidence: [docs/team-validation.md](docs/team-validation.md).
- **Persistence:** additive `players`, `runs`, `hidden_names` tables plus linked `events`, retaining legacy `opened` events. Start and finish each transact the run and its event together. Identical finish retries succeed; conflicting retries return 409. WAL and a five-second busy timeout support the owner commands alongside the server.

### Owner commands

Stats, hide and reset use `DATA_DIR/app.db` (default `data/app.db`). Stats count accepted finishes only, never abandoned starts or legacy opens:

```sh
bun run stats
bun run stats -- --since 2026-11-28T09:00:00-06:00 --until 2026-11-28T10:15:00-06:00
bun run hide "Test Robot"
```

Filters may be used independently and require ISO timestamps with a timezone. Finish time is server time; since is inclusive and until is exclusive. The four stdout lines are `players`, `finished_runs`, `median_runs_per_player` (one decimal, over players with a finish), and `touch_share` (rounded whole percent). A missing database prints zeros without creating it. Bad flags fail to stderr with no partial report.

Hide trims and lowercases the name, hides all players using it, and is idempotent. It accepts now-blocked names and never deletes history. A foreground game-over board observes it within five seconds through cache expiry and polling. Its persisted name key is unchanged by the separate moderation normalization.

Name moderation retains the trimmed 2–16-character ASCII letter/number/space/hyphen/underscore gate and display spelling. It then folds case, removes spaces, hyphens and underscores, maps 0/o, 1/i, 3/e, 4/a, 5/s, 7/t and 8/b, and collapses repeated letters in both names and vocabulary. Normalized blocked terms of four or more characters match substrings; shorter terms match complete names, so `ass` is blocked without rejecting `Jason` or `classic`. Abusive compounds such as `badass` have explicit entries. Exact normalized complete-name exceptions allow ordinary collisions such as `Scunthorpe`, `Hancock` and `therapist`; extensions and numeric suffixes receive no exemption. Reserved names (`colemedin`, `cole medin`, `dynamous`, `archon`, `admin`, `moderator`) use normalized equality before exceptions and return exactly “That name is reserved”; `ArchonFan` and `AdminHelper` remain eligible. Profanity retains “That name isn't allowed. Pick another.” Vocabulary maintenance instructions and the matching tradeoff live beside the list. Updated vocabulary takes effect when the application is deployed, including read-time exclusion of legacy players from both boards, without changing history, personal bests or bet stats. Manual-hide cache expiry and polling remain as above. No moderation runs in the frame loop.

`bun run reset` refuses until passed exactly `--yes` (optionally after `--`). The refusal names the resolved database path. A confirmed reset deletes **all** players, runs (including abandoned ones) and events (including legacy opens) in one immediate transaction. It preserves hidden-name moderation, tables and indexes, and prints deleted counts after commit. A missing database succeeds with zeros without creating files. Stop the server before a pre-stream reset and restart afterwards to clear read caches and in-memory rate-limit buckets; unset the load-test override before restarting. Reset does not selectively remove `load-` names.

### Capacity validation

`bun run load -- --url http://127.0.0.1:43125 [--players 500] [--seconds 60]` writes one new `load-` player and one run per simulated player. The URL must be an HTTP(S) origin. Players start concurrently, die after 5–15 seconds (capped at one-third of shorter invocations), and finish with conservative elapsed-time scores accepted by the normal plausibility rules. At death and acknowledged save they read personal best, top 10 and team totals. Top 10 and teams then poll every two seconds through the deadline; a separate stream-board observer reads those same two data APIs immediately and every five seconds. The observer follows the PRD data cadence without downloading `/board` HTML. This compressed HTTP workload leaves time for sustained game-over polling; it does not simulate a full gameplay duration.

Each request measures through the entire response body, has a five-second timeout, refuses redirects and validates its expected status and essential JSON shape. At the deadline no new requests start; in-flight requests drain within their timeouts. SIGINT/SIGTERM stop scheduling and print a failing partial summary. Output includes requested/accepted players, total requests, failures by HTTP status or timeout/transport/invalid-response category, and count/p50/p95/p99 latency by route and overall (nearest rank over raw samples, including failures). Empty percentiles are `n/a`. A pass requires every player to start and finish, successful observations of every read route, no failed requests, zero 5xx and at least 95% of all requests succeeding in strictly under 200 ms. Failures or an incomplete workload exit nonzero.

The defaults are 300 starts per client IP and 40 per player id per rolling ten minutes. For a dedicated benchmark server only, `LOAD_TEST_START_LIMIT=10000` explicitly raises the IP ceiling, also in production mode; the player ceiling remains 40. It accepts only positive safe integers and is validated before opening the database; limits above 300 print a startup warning. Restart with a fresh scratch database between smoke and measured runs (reset alone does not clear the limiter). Reproduction commands and factory measurements: [docs/load-validation.md](docs/load-validation.md). The timed benchmark is manual; `bun run check` runs its short deterministic tests only.

## Hosting
- Railway, from the `Dockerfile`, with a volume mounted at `DATA_DIR` and GitHub auto-deploy on `main`, so a merged change reaches players within minutes. One instance (SQLite needs one long-running process with a disk). The owner sets up the Railway project; the app only has to honor `PORT` and `DATA_DIR`.
- For a single Railway ingress that appends the actual caller's address to the right of `X-Forwarded-For`, use `TRUST_PROXY_HOPS=1`. Verify that ingress assumption using the procedure below before enabling it; local tests prove application selection, not Railway's header ordering.

### Pre-stream proxy verification

Use an isolated Railway deployment with scratch data and the same ingress configuration as the stream deployment. Temporarily log the TCP peer, complete `X-Forwarded-For` chain and selected client address at the request boundary. Send requests from a known network with (1) no supplied header, (2) `X-Forwarded-For: 192.0.2.10`, and (3) `X-Forwarded-For: 192.0.2.10, 192.0.2.11`. Confirm that the rightmost entry is always the actual caller address and that selection with one trusted hop is unchanged by those forged prefixes. Repeat from another network and confirm the selected address changes to that caller. Remove the temporary diagnostics afterward. If the ingress replaces or orders the header differently, record the observed mismatch for correction and do not enable the setting or claim deployment acceptance. Railway ingress has not been verified by the local application tests.

## Boundaries
- No API keys and no outside services. The app starts and `bun run check` passes with no `.env`.
- Public on the internet during the stream: the API accepts only well-formed requests with capped sizes, at most one score per run id, scores that pass the plausibility check, and at most 300 start attempts per client IP and 40 per player id per rolling 10 minutes (`START_LIMIT`, `PLAYER_START_LIMIT` and `START_WINDOW_MS` in `app.ts`).
- JSON bodies are capped at 4 KiB. Scores must equal `10 * squashes + seconds`. Submitted gameplay seconds must not exceed either whole server elapsed seconds or 300 seconds; squashes must not exceed `floor(4.5 * submitted seconds)`. Choice pauses earn no additional squash allowance, and wall-clock age has no cap. Constants live in `rules.ts`; calibration is recorded in [docs/pacing-validation.md](docs/pacing-validation.md#score-plausibility-calibration-issue-34).
- Peer IPs come from Bun. `TRUST_PROXY_HOPS` defaults to `0`: forwarded headers are ignored unless `TRUSTED_PROXIES` lists the exact peer address. That legacy comma-separated trust list walks the header from the right while the current address is trusted; avoid trusting public client addresses. Positive hop counts take precedence over that list and select the n-th address from the right: for `192.0.2.10, 198.51.100.20, 10.0.0.9`, `1` selects `10.0.0.9`, and `2` selects `198.51.100.20`. Prepending forged entries cannot change selection at a fixed trusted depth. The setting accepts only canonical nonnegative decimal safe integers; invalid values fail before SQLite opens. Missing, malformed or too-short headers fall back to the original peer without throwing. Every entry must be a literal IPv4/IPv6 address; empty entries, hostnames, ports, brackets and zone identifiers invalidate the entire chain without shifting positions.
- Positive hops assume **all** traffic reaches the app through that trusted proxy depth, with the proxy appending the actual caller address. Never enable this on a directly exposed listener or an unverified shorter ingress path: a direct caller could supply the selected entry. This is deployment trust, not authentication.
- After bounded body handling, each start checks and charges the IP budget before JSON parsing. A valid UUID then checks and charges its lowercase player-id bucket before name/team validation or database writes. Invalid requests consume IP attempts; valid-ID attempts also consume player attempts; player refusals consume an IP attempt. Refused buckets do not gain timestamps. Both limits return HTTP 429 with `Retry-After` in seconds (rounded up from the oldest live attempt, at least one); IP checks win if both are exhausted. Attempts at or before the ten-minute boundary expire. Refusals create no players, runs or events. Finish and board routes remain usable, including saving already-issued runs. Both budgets are in memory and reset on process restart.
- Nothing the player does depends on a server response; a run plays with the API down.

## Upgrade contract and choices

`src/shared/upgrades.ts` owns the four ids, names and 20-second interval. Finish requests carry acquired upgrades as `{ id, count }` entries, once each in registry order. Counts record picks, independent of remaining combat resources. The server accepts legacy omitted upgrades as `[]`, validates total picks against survival seconds, normalizes ordering and includes the normalized build in identical-retry comparisons. The existing `runs.upgrades` JSON column and its linked `run_ended` event commit together. No additional event payload or migration is needed. Choice pauses need no server-clock change: elapsed time is an upper bound.

`game/upgrades.ts` maintains counts and three distinct seeded offers. Its independent LCG starts at `seed XOR 0x9e3779b9`, leaving spawn randomness untouched. Choice numbers reject delayed selections. The simulation clamps steps at each 20-second gameplay boundary, resolves that interval, and offers a choice only if still alive. Pending choices freeze all gameplay and cooldowns. Selection applies the upgrade synchronously, increments the next boundary and rejects stale run tokens and choice numbers. There is no run cutoff.

The fixed stepper drops catch-up accumulation at choices and resets its timestamp on resume. Feedback receives the actual shortened active duration. The engine clears steering and pointer capture on either transition, freezes visual time during choices and resets the effects clock on resume. Blur/visibility/rotation preserve the pending choice. Session subscriptions publish only transitions and guard readiness, not combat frames.

Release, cancellation, lost capture, blur, visibility changes, either choice transition, death, restart, run replacement and unmount clear touch ownership and its overlay. Ownership is cleared before releasing capture, making resulting lost-capture events harmless. Delayed touch moves cannot revive input without a new down. Death retains held-key restart protection and advances its existing effects; a fresh touch can restart after the 800 ms guard but stays stationary until dragged.

React displays a native modal dialog with three large button cards, no countdown or dismissal, focus containment and focus restoration to the canvas. Cards fade in for 350 ms and expose aria-disabled during that guard while remaining focusable. Reduced motion omits the fade, retaining the delay. Fresh 1-3 keys and touch cards share Session.choose; touch selections mark input attribution. Finish and game-over use the same deeply frozen count summary, isolated from restarts and late API responses.

Session owns monotonic deadlines: 800 ms from death before restarting and 350 ms from the first publication of each choice before selecting. Eligibility is inclusive at the deadline and checked again by Session on every activation; published readiness is only for presentation. Initial entry remains immediate. A single injected one-shot scheduler publishes readiness while subscribed, reschedules only the remainder if called early, and cancels on replacement, selection, superseding death or final detachment. Deadlines survive detach/reattach; stale callbacks are harmless. Readiness does not use the frame loop, reset board polling or make network requests.

Game-over results render immediately, with space reserved for the replay instruction and button until the guard expires. Canvas, overlay, keyboard and assistive activations all pass through Session.restart. Overlay and card gestures must begin after eligibility; early downs released after the deadline do nothing. Early activation keys remain blocked through release, including native Space keyup clicks; fresh presses work afterward. Rejected inputs never attribute touch, steer, acquire capture, start an API request or queue an action. Choice gameplay remains frozen throughout. Chrome evidence and reproduction: [docs/guard-validation.md](docs/guard-validation.md).

Contact can consume a shield charge or health and grants one second of immunity, but never removes the attacker. Bugs remain alive until a projectile or bomb kills them; moving away ends contact without a free clear. This keeps immunity from providing passive crowd control, and only weapon kills award squashes.

Review laser gives new shots `1 + picks` penetrations and a longer procedural streak. The first pick also multiplies the robot’s 1.5-second firing interval by 0.25 (0.375 seconds, 4× firing rate); that benefit never stacks. Acquisition clamps the remaining robot cooldown without firing synchronously; repeats leave it alone. Combat and the first card share `laserFireMultiplier` in `src/shared/upgrades.ts`; later cards describe additional penetration. Swept collisions resolve by segment entry time, then bug id; victims are removed once, preserving survivor ordering for feedback. Shots retain their creation-time budget and lifetime. The benchmark accepts `?profile=laser` to exercise this path with two picks.

Test shield refills available charges to `min(picks, 4)`: one initially, two on the second pick, then capacity increases twice more. Later picks refill spent charges at that cap without healing.
