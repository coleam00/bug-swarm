# Stream board validation

Validated on Windows with Bun 1.4.2 and Microsoft Edge 157.0.4341.60 (headless Chromium). Measurements are in [board-evidence/measurements.json](board-evidence/measurements.json).

`bun install`, `bun run check` and `bun run build` pass. The check ran 161 tests with zero failures. The focused board, route and production-handler tests cover mapping, validation, empty/zero states, identities and ties, highlight deadlines, independent polling, 2/4/8/8-second retries, recovery, out-of-order responses, slow reads and lifecycle cleanup. The actual React renderer test exercises subscriptions, stable keyed rows, waiting/reconnecting text, text-only names, origin-derived links and unmount/remount. Existing API deadline tests still cover five-second body timeouts.

## Browser evidence

The production entry's real Hono/static handler served `/board`, `/board/` and the built assets through Playwright request interception. Development used Vite's actual HTML/module transform pipeline and the same API handler. This exercised the default production build and the development module graph, including React StrictMode. No network listener was opened: `Bun.serve` was captured, HTTP requests were fulfilled in process, and browser WebSockets were closed. Every database, browser profile, home and dependency used for this probe lived in scratch directories; all database handles, browser processes and Vite watchers were closed afterward. Playwright was installed only for validation, with no project dependency added.

Ten synthetic database players had 16-character names (`WWWWWWWWWWWWWW00` through `WWWWWWWWWWWWWW09`) and scores from 999,999 down to 988,893. Their real leaderboard and team responses populated the board. The initial production view became ready in about 236 ms in this local harness.

- [1280×720](board-evidence/1280x720.png): all ten rows and the join footer fit without scrolling. Names and scores measured 40 px; team totals measured 64 px. All maximum-length names were fully visible. DOM order is 1–10; visual order is 1–5 down the left, then 6–10 down the right.
- The same rendered page resampled to [640×360](board-evidence/640x360.png) (quarter area) and [320×180](board-evidence/320x180.png) (quarter dimensions) retains clear, high-contrast names and scores. At the smaller size, names/scores are effectively 10 px and totals 16 px; the small footer is supplemental to the stream's shared game link.
- [390 px portrait](board-evidence/390x844.png) and [844 px landscape](board-evidence/844x390.png): one ordered column scrolls vertically, with no horizontal overflow. A 320 px viewport also passed. Separate maximum-safe-integer fixtures passed at 1280, 390 and 320 px; compact numbers fit, with exact values in accessible labels and titles. The race keeps both labels/totals visible even when one team has zero points.
- In reduced-motion mode, race transitions measured zero seconds. Highlights retain their temporary static outline/background; the desktop screenshots use this mode.

The browser probe then returned HTTP 503 for leaderboard reads only, while team reads continued. Existing names/scores stayed visible with “Reconnecting…”. Adding a higher-scoring Spaces player changed the race and highlighted the overtake while the leaderboard remained unavailable. On recovery, the new entry appeared and highlighted without replacing the page shell. Highlights expired without being extended by the next unchanged poll. A subsequent outage of both endpoints retained all ten rows ([screenshot](board-evidence/outage.png)); reloading into an outage kept the complete shell and waiting placeholders, with no invented zero scores. Recovery restored the data and cleared the status.

Against the scratch database, the actual `bun run hide "New_Robot_123456"` command removed that name from the visible board and its score from the displayed Spaces total in about 2.15 seconds. Team totals returned to Tabs 4,975,315 / Spaces 4,969,145. This was checked while reads succeeded; a name hidden during an outage can remain in the retained last-good snapshot until recovery.

Browser traffic contained only board GETs: no run-start, finish, player-best or other mutation requests. Production loaded the board chunk and its CSS, with no App chunk. Development loaded the board module, with no App, identity or engine module. There were zero browser page errors. The join anchor displayed and targeted the actual page origin, `http://board.test` in the harness; browser-free rendering tests also check HTTPS and an origin with a port.

## Limits and reproduction

The ordinary `bun run dev`/`bun run start` TCP listeners were not launched because this task requires socket-only isolated servers. The probe exercised their serving components without listeners; production route/asset tests and the existing dev-launch test additionally check the real entries. The development proxy's actual network forwarding was not exercised. Edge provided Chromium coverage; installed Chrome rejected remote debugging during launch. No physical phone, non-Chromium browser or real livestream encoding was tested.

To repeat the visual check, use a fresh scratch home and `DATA_DIR`, seed ten validated 16-character names with finished scores through `startRun`/`finishRun`, build, and open `/board` through a server you started with those scratch settings. Check 1280×720, downsample that screenshot to 640×360 and 320×180, then check portrait/landscape phone widths. Return 503s for one and both GET endpoints to check retention/recovery; add a new leader and reverse the team lead to check temporary highlights. Run the hide command against that same scratch `DATA_DIR`, and observe both leaderboard and totals within five seconds of healthy reads. Close the server/database before deleting scratch data on Windows. The separate Phase 3 load script is outside this change.
